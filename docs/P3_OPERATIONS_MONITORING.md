# P3-02 运行监控与异常诊断

## 本批交付

本次只增加**进程内、有界的运维可观测性**，不接入任何外部监控服务，不改业务查询语义。管理员在「系统管理 → 运行监控」手动刷新查看：

- 进程启动时间、已运行时间；累计 API 请求、成功、4xx、5xx、401/403、超过 3 秒的慢请求次数，以及最近故障、最近慢请求时间；
- V2 查询的并发上限、正在执行数、正在等待数、已被限流总数；
- 元数据库 `SELECT 1` 就绪探测结果和探测耗时；使用 HikariCP 时附加展示连接池活跃、空闲、等待及总连接数。

监控在内存中只保留固定数量的 LongAdder/AtomicLong 计数器，**不保存**请求路径、IP 地址、用户名、请求体、SQL、数据集字段、密码或异常原文；**进程重启后清零**，不能代替审计日志或持久化指标时序数据库。

## 接口及访问控制

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/health` | 匿名 | 原有进程存活（liveness）；不依赖数据库 |
| `GET /api/ready` | 匿名 | 元数据库 `SELECT 1`，成功 HTTP 200 且 `{"ready":true}`，失败 HTTP 503 且 `{"ready":false}` |
| `GET /api/admin/operations/status` | 仅 admin 会话 | 运行指标、元数据库状态、V2 限流及可用的 Hikari 连接池指标 |

所有响应不包含源数据库主机、密钥和 SQL；`ready` 只返回布尔值并禁止缓存。读者（VIEWER/EDITOR）不能调用管理接口。

业务查询并发限制延续现有 `AnalysisQueryLimiter`：同时最多 4 个 V2 查询，等待上限 250ms。现在可以通过监控确认活动数和拒绝数；繁忙时正常返回 **HTTP 429**，提醒用户稍后再试。该限流器是**单实例**的，部署多实例时不能当作集群级并发限制。

## 值班排障建议

1. `/api/health` 非 200：优先检查服务进程、启动日志、端口和反向代理。恢复服务后再检查 `ready`。
2. `/api/health` 正常但 `/api/ready` 为 503：检查元数据库服务器、连接池耗尽、网络、权限及 H2 文件锁；**不要通过清空数据库、删除锁文件或覆盖恢复来“修复”**。
3. 管理员页面中的等待连接数连续大于 0：排查慢事务、连接池及元数据库响应。探测语句仅为 `SELECT 1`，不检测任一 StarRocks/MySQL **业务数据源**。
4. V2 活跃查询长期等于并发上限且拒绝数持续增加：查看只读数据源的慢 SQL、查询计划与网络。先降低报表刷新频率，再评估 SQL 与容量；不建议通过无限放大并发数掩盖问题。
5. 5xx 或慢请求增加：结合服务器本地日志排查故障时段。监控面板不记录异常内容；检查日志时谨慎保护敏感数据。
6. 确认元数据库损坏时，使用独立备份和隔离空库恢复流程，详见 [P3_METADATA_BACKUP_AND_RECOVERY.md](P3_METADATA_BACKUP_AND_RECOVERY.md)。先演练，再根据批准的运维切换方案处理故障。

可将 `/api/ready` 用于外部负载均衡或监控探测；**不要**将管理员监控端点作为公开探测地址。当前并不含自动告警推送、服务自愈、跨节点高可用、持久化历史指标或自动切换主库。

## 定向验收

- `OperationsMonitoringTest`：H2/失效 JDBC 的 readiness 200/503，匿名响应不得泄露连接详情；计数器 2xx/4xx/5xx/401/403 与不采集凭据；管理员/普通读者的访问隔离；V2 并发占用、释放和被拒绝次数；普通读者的查询繁忙 HTTP 429。
- 前端 TypeScript 和 Vite 构建验证监控页面入口与数据结构。
- 范围明确：未执行全量回归、真实生产数据库断网演练、负载压测或生产发布。

此批完结的是**基础运维监控**，不是 P3 全部可靠性任务。
