# P3-03 数据源故障隔离与恢复检查

## 适用范围

本阶段只保护 **V2 分析查询及普通用户已发布 V2 图表查询**的 JDBC 源连接。传统 V1 查询和原始管理工具仍使用其原有连接流程，不宣称已全系统覆盖。

新增 `SourceRecoveryGuard`：以 `connection_id` 为键，在当前 JVM 内存中跟踪每个数据源的短时连接故障；不保存主机、密码、SQL、查询结果或用户信息。

- 同一数据源连续发生 **两次连接类 JDBC 异常**（SQLState 08xxx、`SQLTransientConnectionException`、`SQLRecoverableException`），暂停新的 V2 查询 30 秒。
- 暂停期间直接返回脱敏后的 HTTP **503**，不会继续尝试建立此数据源连接；不会重试用户 SQL。
- 30 秒后仅放行**一个**半开试探查询；成功则恢复正常，仍断连则再次熔断 30 秒。其他并发访问不会同时向故障源发起探测。
- 普通语法错误、非法数据集或过滤字段等非连接类故障**不会触发熔断**，以免误判源数据库宕机。
- 每个实例最多跟踪 500 个源的状态。服务重启后状态清空；不是跨实例分布式熔断器。

现有 V2 分析查询仍保留只读权限校验、并发 4 和等待 250ms、JDBC 查询超时。数据库只读权限需要使用受限的源账号保障；JDBC `readOnly` 只是一项驱动提示。**不会自动重放 SQL、不会自动进行写入、不会隐式无限重试**。

## 管理员恢复流程

“系统管理 → 运行监控”增加数据源隔离状态表，显示数据源名称、关闭/熔断/等待探测/探测中、连续失败次数、冷却剩余秒数：

1. 先确认源数据库进程、网络、账号权限和连接池（例如 StarRocks FE 的 MySQL 协议端口）。
2. 熔断期内不要连续点击检测；在冷却完成后点击“检查连接”，后端只对该源执行强制 JDBC 只读的 `SELECT 1`，不执行原分析 SQL。
3. 检查成功会关闭该数据源熔断状态；失败会继续隔离并返回统一脱敏错误。源连接检查由现有管理员会话和 CSRF 校验保护。
4. 如果系统元数据库本身不可用，应先按 [P3_OPERATIONS_MONITORING.md](P3_OPERATIONS_MONITORING.md) 使用 `/api/ready` 确认原因，不要将两类故障混淆。

新增管理员专用接口：

| 接口 | 功能 |
| --- | --- |
| `GET /api/admin/operations/sources` | 读取已配置数据源名称、熔断状态及剩余冷却期；**不提供主机、登录凭据或 SQL** |
| `POST /api/admin/operations/sources/{id}/recheck` | 经既有 admin + CSRF 认证后手动执行只读连通性检查；冷却期未结束时拒绝重复连线 |

## 可预期的失败行为

用户请求遇到连接类异常时收到 **503**，并显示“数据源暂不可用，请稍后重试”。管理员/读者均不应在响应中看到 JDBC 连接 URL、数据库主机、驱动异常或连接密码。

H2 定向故障注入测试 `SourceRecoveryGuardTest` 验证两次断连、同源短路、独立数据源不受影响、半开单探测、冷却结束恢复、语法错误不触发熔断、敏感异常信息不外泄；`OperationsMonitoringTest` 验证管理员数据源列表过滤敏感字段、冷却时拒绝重复检查及 POST 必须携带 CSRF。

## 尚未完成

- 真实 MySQL / StarRocks 宕机、FE 重启、慢 SQL 或网络分区演练；
- 跨实例共享熔断状态、主动告警及持久化运行时间序列；
- V1 老查询路径、任意 SQL 预览和数据源配置测试等其他 JDBC 路径的统一故障保护；
- 网络连接成功但权限错误、SQL 执行慢、业务表消失等语义故障的自动诊断；
- 生产部署与全量回归。

此批属于**有限故障隔离与人工恢复检查**，不是完整自动自愈或生产级高可用。
